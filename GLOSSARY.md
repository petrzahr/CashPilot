# Glossary

Domain terms used in code, docs and architecture reviews. Code for these lives in `src/services/accountScope.ts` unless noted.

**Default account** — the account marked `isDefault` that is not archived (`getDefaultAccount`). Budget KPI tiles, the category overview, mandatory expenses and Analytics are computed from it only. There is at most one; there may be none.

**Effective amount** — the amount a transaction counts with everywhere: an executed item uses `actualAmountInHaler` when set, anything else uses the planned `amountInHaler` (`getEffectiveAmountInHaler`). A planned item never uses a stale actual amount.

**Account flow** — the signed effect of a transaction on one account (`getAccountFlowInHaler`): income and incoming transfers add, expenses and outgoing transfers subtract. A transfer to the same account and a balance adjustment have no flow; corrections are handled by the forecast.

**Net transfers** — transfers seen from the default account, netted per counterparty account: outgoing counts +, money returned to the default account counts −. Both the Saved / Invested KPI tiles and the "Savings & transfers" row of the category overview use net transfers, so they always agree.

**Account balance** — the state of one account at the end of a day (`getAccountBalanceAtDate` in `src/services/accountBalance.ts`); 0 before the account's activation date. A liquid account is its initial balance plus the effect of its transactions plus legacy corrections not already stored as transactions. An investment or pension account is its latest valuation up to that day (market value snapshot, else the market value on the account) plus account flows after it; corrections never apply. By default only executed items count (actual balance); `includePlanned` gives the projected balance used for reconciliation and the forecast opening.

**Forecast** — the module that, from data, today and the ranges, computes summaries for all periods (`calculateForecast` in `src/services/financialEngine.ts`). It builds its own period sequence (`buildForecastPeriods`): 12 periods back and 12 ahead of the current period, the data bounds, the Overview and Analytics ranges and the selected period. Screens never push bounds into it. `usePeriodForecast` (`src/hooks/usePeriodForecast.ts`) holds today, the current and selected period, the screen ranges and the memoised forecast.

**Period view** — the answer to `forecast.getPeriod(key)` for one period key (`PeriodView` in `src/types/finance.ts`), undefined outside the forecast's period sequence: `{ period, projected, recorded, items, defaultAccount, defaultAccountSplit, actual }`. Screens show `projected`; only the per-item source account running balance on the Budget screen uses `recorded`. `defaultAccount` holds the Budget tiles and KPIs of the default account — opening, income, expense, net transfers, net change, closing, closing with overdraft (`getOverdraftLimitInHaler`), overdraft exceeded, actually saved (income − expense + corrections), saved and invested (net transfers to savings, resp. investment and pension accounts) and their percentages of the default account's income. It is computed on first access from the projected summary and the forecast's own effective items, then remembered; all zero (closing with overdraft = the limit) without a default account. An account activated inside a period after its first day opens at 0 and its initial balance counts in the net change. `items` are the period's effective items (stored items and virtual occurrences, cancelled included). `defaultAccountSplit` splits the default account's income, expense, corrections, net transfers, actually saved, saved and invested into `executed` and `planned`, which add up to `defaultAccount`: planned are the remaining items (`isRemainingPlanned`: not cancelled, and not executed with a date up to today), executed is the rest; corrections are always executed. Each part's percentages are of that part's own income. `actual` exists only for the period that contains today: the actual account balance of every account today, and the usable and net worth sums of those balances; the Budget and Accounts screens show it (and the executed split) as a small unlabelled number under the end-of-period values.

**Projected summary** — a current or future period with investment and pension accounts anchored at today's market value (`forecastPeriods` of the forecast); for a past period it is the recorded summary, since there is nothing to project.

**Recorded summary** — a period summary built from stored values, with no projection (`periods` of the forecast).

**Virtual occurrence** — an occurrence of a recurring rule in one period that is computed from the rule (and its period exception), not stored as a transaction. Its ID is `virtual_<ruleId>_<periodKey>` (`buildVirtualId` / `parseVirtualId` in `src/services/transactionCommands.ts`). Editing it or changing its status stores it as a real transaction (it materialises); a manual position in its day is remembered by the period exception.

**Edit scope** — what an edit of a recurring item changes (`RecurringMode`): `occurrence` only this period (a period exception, or the materialised transaction); `future` this occurrence and later, by splitting the rule at its date into an old branch and a new one that carries the change; `series` the whole rule including already materialised past occurrences. With a new position in the day, `future` and `series` set the order in the same command (`updateRecurringRule` with `placement`).

**Transaction form** — the item form as pure data (`src/services/transactionForm.ts`): defaults for new, edit and duplicate, field transitions, options, validation and the save action that `TransactionModal` dispatches to one command.

**Command** — a pure function that changes app data: `(data, input, ctx) → { data, outcome }` (`src/services/transactionCommands.ts`). It never touches React, storage or toasts; `ctx` supplies the current time, today's date and new IDs, so tests can fix them. `FinanceContext` is only the adapter: one runner, `perform(command, feedback)`, runs the command through the sync controller and turns the outcome into a toast or an undo action via its command feedback. When nothing changes, a command returns the original data object.

**Command feedback** — what the user is told after an action (`src/services/commandFeedback.ts`): one pure function per action, `(outcome, input) → { toast?, undo?, rejected? }`. `toast` is the Czech text and type; `undo` is the command behind the toast's "Vrátit" plus the toast shown after undoing (`perform` runs it with today from the context at click time); `rejected` marks an outcome the command refused, with the message for the caller. All action toast texts live here, none in `FinanceContext`.

**Action result** — what every data action of `FinanceContext` returns (`ActionResult` in `src/services/commandFeedback.ts`): `{ ok: true, value }` or `{ ok: false, reason, message }`. `not-saved` means the change was not written (data still loading before the first sync, or the storage write failed); `rejected` means the command refused it (invalid input, account or category in use). Actions never throw; callers show `message` where a form needs it, and `perform` has already shown the toast.
